先看总体：这份 PR 适配了什么

#21892 把 Ascend 原有 PCP 与 main 已有的 HiSparse 基础后端接起来。核心是把一套批次信息拆成两种用途：本 rank 的查询布局负责 attention；各 rank 汇合后的写入布局负责 Resident 和 Host KV。请求的生命周期、驻留调度与完成通知继续交给 vLLM Core。

先记住三个结论

  1. 不是只放开一个开关。旧代码把查询数当写入数；PCP 下查询可分片、重复或补齐，写入却必须覆盖汇合后的 KV。
  2. 不新增注意力算法或自定义 kernel。本 PR 没有 C++ / Triton 算子文件修改；复用现有 Prolog、PCP AllGather、packed scatter、HiSparse resolver / SFA 和 DMA。
  3. Core 源码没有修改。Ascend 新增一个 ActiveKVConnector 子类，以及按需安装的 cache-handle / mirror 方法适配；“没有 Core 提交”不代表“没有改变 Core 对象的运行行为”。

先分清坐标：local query、gathered write、canonical request

这里容易混淆的不是“有几份 KV”，而是同一个 token 在不同表里使用哪种行号。canonical request 指全局批次里的原始请求序号；persistent state slot 是 idx_mapping 指向的长期状态槽，二者也不能混用。

字段 / 对象它的顺序和用途
local_batch.idx_mapping本 rank 的 query 请求行 → persistent state slot；dual-chunk 可重复同一个请求，图 padding 也在这套长度里。
global_batch.req_ids / idx_mappingCore 的 canonical 请求生命周期与 residency 更新，不能替换成本地重复的请求列表。
_padded_gather_idxall-gather 行 → 全局批次 token 下标；顺序是 rank-major。
_gathered_kv_slot_mappings每个 KV group 的 all-gather 行 → 实际写 slot；padding 行是负槽。
local_tables[host_group] / Hot table沿 query 请求行查逻辑源页 / 热缓存，不是写入行列表。

新增字段的来源非常直接

AscendPCPAttentionContext.local_request_state_indices 在三个 context 构造位置分别赋值：capture 用 input_batch.idx_mapping；复制执行路径也用当前 input batch；正常分片路径用 local_batch.idx_mapping。它把已经存在的状态映射显式送到 HiSparse metadata builder，没有另建请求编号体系。
