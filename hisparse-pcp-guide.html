CODE-VERIFIED GUIDE · A5 / C8

HiSparse 管缓存，
PCP 改行布局。

vLLM Core 负责缓存生命周期与调度；vLLM Ascend 接上 NPU 数据搬运和稀疏注意力。叠加 PCP，关键是让查询、KV 写入、Host 镜像各用正确的行映射。

基础 HiSparse：主 KV 历史以 CPU DRAM 为后备，HBM 保留 Resident 与 Hot；Decode 按 TopK 补齐缺失行。

当前 PCP 补丁：支持指定 C8 / request-sharded target decode 路径；不新增计算 kernel，但扩展 Core 的运行时接线。

PD 分离：比混部多一层跨引擎 KV 传输；当前 Ascend 补丁尚未打通这个组合。

01 / OWNERSHIP

两层框架，四种存储职责

vLLM Core：定义“谁拥有什么”

layout 划分缓存组；coordinator 随调度维护请求、页、固定与失效；runtime 把逻辑 TopK 变成可供注意力读取的物理索引；HiSparseConnectorWorker 执行 Host 镜像和状态同步。

vLLM Ascend：实现“在 NPU 上怎么做”

platform 指定 AscendHiSparseBackend；后端提供 Host 内存注册、缓存视图与设备操作；AscendHiSparseImpl 把 Prolog、Indexer、换入和 SFA 串起来。

位置职责生命周期 / 回收方式
Host Source
CPU DRAM		主 KV 历史的持久后备，按页管理。接收 D2H 镜像；最新尚未完成写回的行可暂时只有 Resident 副本。
Resident
HBM		主 KV 的页级驻留 / 写回缓存；Prefill 与 Decode 产生的新 KV 都可写这里。脏页必须保留；Host 副本完成且满足 Hot 读取条件后可解除固定，内存池复用时撤销旧映射。
Hot
HBM		每请求容量有界，保存从 Host 补回的 TopK token 行。Resolver 按请求处理当前查询集合，保护命中行，再按 LRU 为缺失行选槽。
Indexer KV
设备缓存组		为 Lightning Indexer 计算 TopK 提供索引 KV。独立于主 KV 的 Source / Resident / Hot；不能把主 KV 卸载理解为 Indexer KV 也全部卸到 CPU。

注意：Resident 和 Hot 都只是主 KV 在 HBM 上的部分副本，定位不同；不是所有数据必须依次经过“Resident → Hot”。Resident 命中的 KV 可直接被注意力读取。

02 / REQUEST LIFECYCLE

先产生并写回，再按 TopK 读取

① 写入：Prefill / Decode 都会产生新 KV

Prolog计算本步 Q / KV；C8 路径生成量化 KV。
→
Resident按 slot mapping 写入本步 KV 行。
→
Host 镜像按镜像 slot 将 KV 写回 DRAM，完成后发布状态。
→
Coordinator根据持久副本和 Hot 准备情况推进页状态。

本导读的 Ascend 路径使用 Core eager Host mirror。D2H 是带事件 / 完成状态的过程，不能把“已经发起”当作“Host 已可读”。

② Decode 读取：先命中，再补缺失

Indexer → TopK得到每个 query 的逻辑 token 索引。
→
Resolver先查 Resident，再查 Hot；决定缺失行与目标槽。
→
Host → Hot只补缺失行，生成可读物理索引。
→
SFA读取 Resident / Hot 对应的物理 KV，计算输出。

同一请求的多个验证 query 会一起参与 Hot 命中保护与淘汰决策。Core 还按层组进行预取，并通过事件等当前层数据就绪；代码中存在重叠机制，不能据此保证搬运时延被完全掩盖。

Prefill 的读取单独处理：Ascend 先尝试 C8 Resident 直读；不满足时由 stage_prefill_rows 从 Resident / Host 组织上下文，再调用注意力。因此混部开启 HiSparse 后，Prefill 也参与这套缓存管理。

03 / ASCEND EXECUTION

Ascend 接的是什么算子？

环节实际计算 / 调用作用
KV 生成继承 SFA 的 Prolog 与 Lightning Indexer 路径生成 Q / KV、量化并产生逻辑 TopK；Indexer 与缓存管理是两件事。
缓存决策hisparse_resolve_residency（自定义 SIMT kernel）Resident-first、Hot 命中、请求内联合保护、LRU 选槽与物理索引。
缺失行补齐gather_rows_kernel（Triton）通过注册后的 Host 地址，把缺失 KV 行装入 Hot。
注意力C8：npu_kv_quant_sparse_flash_attention_vllm
BF16 分支：npu_sparse_flash_attention		使用已经解析好的物理索引完成稀疏注意力。

04 / PCP COMPOSITION

PCP 要对齐三种视图，不是再写一个注意力算子

PCP 把 Prefill token 的计算分到多个 rank。每个 rank 计算的本地 query 行，与 all-gather 后要写入缓存的聚合 KV 行，行数和顺序可以不同。当前路径的 target Decode 按请求分片；这不等于 DCP 将每个请求的历史 KV 切分。

PCP=2 · 行布局示意（省略 padding）rank 0：本地 query [A, B] → 本地 KV [A, B]rank 1：本地 query [C, D] → 本地 KV [C, D]all-gather 后：每个 rank 的写入视图 [A, B, C, D]

query 用本地映射；Resident / Host 写入用聚合映射。
真实批次还有请求重排、padding、写入 mask 和 MTP 行，不能只把 token 数乘以 PCP。

基础接口为什么不够？固定 Core 的 HiSparseCacheHandle 用同一组 num_actual_tokens / req_id_per_token 准备读写，write_target 还会按 Decode 容量截断。PCP 后若继续把本地 query 信息当写入信息，Resident / Host 镜像就会少写或写错行。

  1. KV 数据对齐：Prolog 先写本地 C8 scratch；按字节 all-gather，保持 C8 latent、BF16 RoPE、FP32 scale；再按 gathered slot scatter 到 Resident。
  2. 读写元数据分开：Source / Hot 使用本地 query 的 block table；Resident 与 Host 镜像使用 gathered slots 和 write request IDs；持久请求状态保留 canonical 全局请求索引。
  3. Host 镜像同步改：写入计数、请求归属、prefill 标记跟随聚合写入视图；不能用“本地没有 Prefill”判断本 rank 没有待镜像的 Prefill KV。
  4. 图与 MTP 配套：固定工作区地址，提前准备镜像 staging；draft prefill 与后续 replicated draft decode 使用相应布局。

尽量继承 Core：PCPHiSparseConnector 仅覆写现有 _build_load_kwargs()：传 canonical 请求及 gathered 写入长度；pre_forward、抢占处理、加载时序与完成流程继续用 Core，不复制 batch。Core 暂无分离 query / write 布局的接口，这部分仍由 Ascend worker patch 衔接。

05 / DEPLOYMENT PATHS

混部处理同一引擎布局，PD 还要处理跨引擎传输

混部：一个 engine

Prefill → Resident / Host → Decode

共享同一套缓存配置与请求生命周期。开 HiSparse 后，Prefill 仍要写 Resident、做 Host 镜像；叠加 PCP 时，上节的读写布局适配直接作用于这个 engine。

当前 PCP 补丁面向这条 direct HiSparseConnector 路径。

PD 分离：两个 engine

P 生成 KV → 传输 connector → D 接收 KV → Decode

P / D 可以分别配置 PCP 和 HiSparse。“P 开 PCP、只有 D 开 HiSparse”不等于一个 engine 同时叠加两者，但还必须完成 P→D 的缓存组映射与传输。

当前 Ascend 基础 / PCP 补丁尚无外部 PD 支持。

Core 中已经具备的 PD 机制

layout.py 将 Host Source 与 Indexer 标为可传输组，Resident / Hot 不参与 KV transfer。固定版本 NIXL 可以按 region 映射远近端组，并按本地目标是 DRAM 还是 Device 分流读取。

组合按 Core 缓存组得到的数据路径叠加 PCP 时要处理什么
P / D 都 HiSparseP Host Source → D Host Source；P Indexer → D Indexer。Resident / Hot 是各端本地状态，不跨端复制 LRU。哪个 engine 同时开 PCP + HiSparse，哪个就需要读写布局适配；另需传输接线。
只有 D HiSparseP 普通设备主 KV → D Host Source；Indexer → D Indexer。需支持异构缓存组映射。P 的普通 PCP 路径与 D 的 HiSparse 可分开分析；D 再开 PCP 才有 D 端同 engine 叠加。

上表是由缓存组定义和 NIXL 读路径说明的数据目标，不是已经验证的 Ascend 启动方案。固定 NIXL 的异构 region-group 映射还限制为 pure MLA、物理 block size 相同。

HiSparse 解决“KV 放哪里、什么时候可回收”。
Core 管状态，Ascend 把 Resolver、搬运与 SFA 接到 NPU。
