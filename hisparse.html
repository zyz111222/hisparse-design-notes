先建立完整的设计地图

HiSparse 不是单个卸载算子，而是把缓存分配、生命周期、执行顺序和稀疏计算一起接入 vLLM。

一条主线：Scheduler 决定哪些页必须保留、哪些页可以回收；Worker 把新 KV 写成 Host 后备；每层 Runtime 将 TopK 翻译为可读的设备地址。Ascend 实现这些地址解析与搬运的 NPU 端操作。PCP 再改变 query 和 KV 写入的行布局。
层次主要对象回答的问题
布局与分配layout.py、各 KV Manager、HiSparseHostPoolHost / Indexer / Resident / Hot 各分配什么、占哪个池？
调度控制面HiSparseCoordinator、HiSparseConnectorScheduler一个页什么时候完整、何时能丢设备副本、何时能发布前缀？
执行桥接ActiveKVConnector、HiSparseConnectorWorker本步开始前绑定哪些映射、何时发 DMA、如何回报完成？
逐层数据面HiSparseCacheHandle → HiSparseRuntime → HiSparseIndexGroup当前 TopK 是 Resident 命中、Hot 命中还是 Host miss？
平台后端AscendHiSparseBackend、HiSparseNPUOps、AscendHiSparseImpl用什么 NPU kernel 解析、拷贝和计算？
PCP / PDPCPHiSparseConnector / Core MultiConnector、NIXL前者处理同一引擎的并行行映射；后者处理跨引擎缓存交付。

从代码组织看，它用了哪些设计方式？

设计方式具体落点带来的约束
控制面 / 数据面分离Coordinator 计划页迁移，metadata 跨进程传递；Worker / Runtime 执行。Scheduler 不能靠发出计划就标记 DMA 完成。
写回缓存与多级副本Resident 接受新 KV；Host 写回完成后作为历史后备；Hot 保存稀疏访问副本。dirty / clean 与 pinned / unpinned 是不同维度，不能合成一个“已卸载”布尔值。
平台策略 / 接口实现Core 通过 Backend / CacheOps 使用平台实现；Ascend 提供 NPU resolver、gather 和 SFA 接口。替换平台操作时仍要遵守 Core 的物理行、事件与失效协议。
包装与模板方法扩展ActiveKVConnector 包装 connector；PCP 子类只覆写 _build_load_kwargs，继承 pre_forward 流程。保留抢占、metadata 绑定和同步加载顺序；不是复制一整套调度器。

四种缓存，两个分配池，三种地址

先区分数据在哪里，再讨论淘汰。Resident 与 Hot 不是两个完全独立、固定切开的 HBM 大数组。

对象保存的数据 / 粒度存储与管理是否交付给远端
Host Source主 KV 的历史后备；按页分配，页内是 token 行。新写入在镜像完成前还不能当作耐久副本。独立 CPU DRAM 池；HiSparseSourceManager 管分配与前缀发布。enable_kv_transfer=True
Indexer模型稀疏索引用的 KV；保留其正常历史布局。它不是 Hot 的索引账本。设备缓存组，走正常索引计算路径。enable_kv_transfer=True
Resident本请求仍驻留在设备的主 KV 页；包括当前写入页和未被回收的历史页。设备共享 backing / BlockPool；页级驻留关系和 pin 由 Coordinator 管。False；本地辅助副本
Hot缺失 Resident 的历史 token 按 TopK 换入后的副本；以 token 为内容粒度，按 blocks_per_request 分配容量。与 Resident 使用同一设备 backing 的兼容 view；请求内 Hot 映射与 LRU 在设备上维护。False；本地临时缓存
地址 / 编号含义必须用的映射
logical token ID请求序列中的第几个 token，例如第 901 个。不同请求的同一编号不是同一份 KV。结合请求和 Source / Resident block table 翻译。
Host row IDCPU 池中的物理 token 行；由 Source page ID 与页内偏移组成。host_page × block_size + offset；Hot 的内容标记保存这种身份。
device row IDResident 或 Hot 在共享设备空间内的物理行编号。注意 allocator 的实际 block stride；C8 SFA 还需转换到原生行布局。
request state index请求在持久状态数组中的槽位；用于 Resident 与 Hot/LRU。不是当前 batch 的第几行；batch 变序 / PCP 分片后仍要正确映射。

类图一：Scheduler 的控制面

Coordinator 管的是页的生命周期。每层 TopK 命中 / miss 的 LRU 决策不在这个类里。

对象拥有的状态不负责的工作
HiSparseSourceManager为历史页分配 Host block；在耐久后发布前缀；Host pool 不足时不能虚报容量。不在每个 attention layer 上跑 LRU。
HiSparseResidentManager请求逻辑页 → 当前设备块；记录 residency 变更。不以“Host 已分配”证明 KV 已写回。
HiSparseHotManager某请求是否需要 / 是否已获得完整 Hot region。不保存每个 token 的最近使用顺序；该顺序属于 IndexGroup 的设备数组。
HiSparseCoordinator页的 valid / pending / pin / publication；把多个 manager 和 worker 完成回报串起来。不执行 DMA 或 SFA。
HiSparseConnectorScheduler把本步调度结果转成 metadata；接收 worker 的计数与完成通知。不把 Coordinator 的 Python 对象直接共享给 worker 进程。

逐个看 Coordinator 的请求状态

字段准确含义不要混淆
valid_pagesHost 副本已经完整的逻辑页集合。不是“这些页目前仍在 HBM”。
pending_pages逻辑页到尚在处理的 transfer ID 的映射。排队传输不等于完成。
ready_prefix_pages从序列开头起连续可用的耐久页数。零散的后部 valid 页不自动延长可发布前缀。
pinned_cleanHost 已完整、但 Resident 仍持有 allocation reference 的页。请求尚不能读 Host 时，不能只因 clean 就释放引用。
unpinned_pages已释放 allocation reference、允许设备池复用的 clean 页。数据与驻留关系仍可能存在；真正复用才撤销。
synced_pages此前已经把驻留状态同步给 Worker 的页范围。不是 Host 写回进度。
stale_pages已同步范围中随后改变了驻留关系、需要发给 Worker 的页。避免 Worker 继续使用已被复用的旧设备行。
publication / _PendingSpill前者记等待发布的前缀；后者记录传输 ID、额外 block 引用、预期与实际完成数。请求释放与 DMA 完成可以不在同一个时刻。
重要的两张表：Coordinator 类注释明确说明，常规 block table 保持 append-only；设备驻留关系的改变通过 take_residency_updates() 发给 Worker。不能靠“旧 block table 里还有那个编号”证明该 Resident 数据仍可读。

类图二：Worker、每层 Runtime 和 Ascend 接口

外层接线控制“什么时候做”，Runtime 与 Backend 控制“用什么数据和操作做”。同名 Connector 在调度端与执行端分别实例化。

  1. ActiveKVConnector 保留 Core 的 pre_forward / post_forward 顺序：先处理抢占、绑定 metadata，再通过 load kwargs hook 启动加载。HiSparse 设置同步 load 标志，保证本步的绑定与 restore 在 forward 前生效。
  2. HiSparseConnectorWorker 处理跨层镜像、页传输、Host COW、驻留表更新和事件完成回报。它不参与每层 TopK 的选择。
  3. HiSparseCacheHandle 是 attention layer 的缓存入口：把模型层写 KV 的 slot、Host 镜像 slot、Resident / Source table 绑定到同一层 Runtime。
  4. HiSparseRuntime / IndexGroup 处理 TopK 解析与换入；同一模型索引组共享解析状态，KV payload 仍按层搬运。
  5. Ascend backend / cache_ops / attention impl 分别实现 Host 注册与 DMA、NPU 解析与 gather、原生 SFA 布局桥接。

混部 Prefill：新 KV 先写 Resident，同时形成 Host 后备

混部是同一引擎同时处理 Prefill 与 Decode。一个 batch 可以包含两类请求，因此全局“有 Prefill”和当前 rank“只有 Decode”也必须分开。

  1. 新 KV 的来源不分 Resident 专属阶段。Prefill 和 Decode 都会产生新 KV；当前写入位置由 Resident slot mapping 确定。Resident 不是“Decode 生产的专用缓存”。
  2. Prefill 不一定先把整段写进 Hot。Ascend C8 在上下文全部 Resident 且满足 eager 几何约束时，直接走 paged Resident Prefill；否则按 staging plan 从 Host 与 Resident 拼出本次 Prefill 的读取缓存。
  3. Host 分配不等于 Host 有效。行镜像用于保存本步新写入；页级传输 / 完成计数用于确定页耐久性与发布条件。数据还在 pending 时，不能按“CPU 已有完整页”回收 Resident。
  4. 当前尾页不能随便 unpin。它仍在追加新 KV；Coordinator 的页回收条件排除了 active tail。

一个请求结束，不代表所有 Host DMA 都结束；前缀命中也不等于旧设备副本还在。Coordinator 必须把这些边界与普通 BlockPool 生命周期接起来。

事件源码中的设计理解要点
本地 prefix 命中commit_computed_blocks 记录可用 Host 页，并安排可能仍存活的 Resident copy adoption。Host 前缀可以比设备驻留更长；不能要求历史全部在 HBM 才算命中。
分块 Prefill 的前缀发布publish_when_ready 记录待发布；_publish_host_blocks_if_ready 只发布 ready_prefix_pages 覆盖的连续耐久部分。不等整段长 Prefill 完成才发布，也不把仅已排队的写回当成命中。
Host block COW / 复制Coordinator 发出 host_block_copies；Worker 按前步 Host write event 排序拷贝，完成后释放额外引用。共享前缀的写入要区分原块与目标块；不能覆盖仍被其他请求使用的内容。
抢占 / preemptionCore pre_forward 先 handle_preemptions；Coordinator.free 区分取消的 forward、待完成传输与发布。已取消的预计算不能凭计划就变成有效 KV。
请求结束释放请求归属；pending transfer / publication 可暂留必要引用直到完成。清掉请求不等于立即复用仍在 DMA 中的源 / 目标块。
设备干净副本保留请求归属解除后，clean Resident copy 可继续留在池中供前缀复用；实际复用再失效。这是可复用缓存，不是旧请求还能无限读取自己已释放的地址。

Core 中的 PD 接口：MultiConnector 调度，NIXL 分组读取，HiSparse 完成导入

这一章解释固定 Core 代码已经提供了什么接口，不据此宣布 Ascend 已能部署该组合。尤其不能把 MultiConnector 理解成两个子 Connector 各自随便接管同一批远端命中。

  1. MultiConnector 是组合与路由层。缓存命中查询逐个问子 connector；首个正命中者成为此请求的 load owner。任何 child 返回“尚未确定”的 None 时，该轮查询需要等待。其他 child 仍收到真实目标 block 信息，但 external token 数是 0。
  2. 跨端不能依赖 group 序号碰巧一致。NIXL pull worker 对不同 group / region 布局有重映射路径，并限制为纯 MLA 和相同 physical block size；这不是所有异构 KV 布局都自动通用。
  3. Host 与 Device 使用不同传输描述符。_read_blocks_mixed 按 region 是否 DRAM 分类，分别用 local_dram_handle / local_device_handle 发 READ。代码里共享 Host 区域可让非 rank0 跳过 DRAM transfer；该策略不能直接套到当前 Ascend 的每 rank 私有 Host 池。
  4. Host import 有明确的完成边界。Coordinator 记录 pending import；接收成功后才把完整页标 valid，并推进 ready_prefix_pages；对最后一个已计算 token 所在页安排 restore。失败接收不能按成功发布。
  5. 页恢复与 Hot 换入是两个机制。这里的 restore 为导入后的本地继续计算准备页；普通稀疏 Decode 仍按 miss token 从 Host 搬到 Hot，而非每步恢复整个前缀。
当前缺口很具体：Ascend 的 adapt_pcp_connector() 检查直接 HiSparseConnector；如果内部是 MultiConnector 就抛错。因此上述 Core 机制还没有通过当前 PCP wrapper 接到外部 PD 传输，不能用“上游有接口”替代组合适配与验证。
