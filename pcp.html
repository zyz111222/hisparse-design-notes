先把 PCP 单独看清楚

本篇先不启用 HiSparse，只解释固定版本的 PCP 管理器与 Ascend SFA 数据路径。读懂这里的三种行顺序，下一篇的组合适配才有基础。

PCP 的任务：把同一引擎本步的 query 工作拆给多个 rank，组织新 KV 的交换与正确落位，最后把 hidden states 恢复为全局请求顺序。它本身不建立 Host / Resident / Hot 分层缓存。
对象职责与下一篇的关系
Core PCPManager建立全局 batch → rank-local batch 的切分和恢复映射。组合适配继续使用这些映射，不能重建另一套请求编号。
AscendPCPManager : PCPManager承接 Ascend CPU 长度视图、attention 状态、graph padding 和 draft 布局。向 attention / HiSparse 提供同一份 AscendPCPAttentionContext。
Ascend SFA backend按 PCP 策略交换本步新 KV，再按 gathered slots 写入缓存。组合适配还要把正确写行镜像到 Host，不能只看本 rank 的 query。
restore_for_sampling汇集并恢复全局 hidden states，交给采样或 draft。HiSparse 的局部 query 布局不能泄漏成全局采样顺序。
这里的“原生 PCP”指在同一固定源码版本上关闭 HiSparse 后走的 PCP 路径；不是拿最新 main 代替本文版本。PCP 与 DCP 是不同维度，本篇以 PCP > 1、DCP = 1 为主要叙述范围。

Prefill 怎么切，Decode 怎么分

不能只记住“PCP 切 Prefill”。固定版本里也存在按请求分片的 Decode 策略，具体是否启用由模型与并行配置决定。

Prefill：首尾配对的 DualChunkSwap

  1. 对一条需要分片的 query，取 2 × PCP world size 个 chunk；chunk 长度向上取整。
  2. rank r 取第 r 块和倒数第 r 块。PCP=2 时，rank0 取 chunk0 / chunk3，rank1 取 chunk1 / chunk2。
  3. 首尾配对是分工方式；rank 的实际本地 batch 还会组合多请求，并为 collective / graph 补齐。不能把本地行号当原请求 token 位置。

Decode：复制执行与按请求分片分开理解

模式计算归属新 KV 的处理
replicated decode各 PCP rank 看到相同 Decode query。重复行只保留规范写者；没有其他分片工作时无需重复交换相同 KV。
request-sharded decode本步 Decode 请求按 ordinal % PCP world size 分给 owner rank。owner 计算的新 KV 要交换；hidden states 随后也恢复全局顺序。owner 无需跨 step 固定。
Ascend 策略非 KPool 模型，PCP > 1 且 DCP = 1 时启用 decode sharding；KPool 分支返回 False。模型例外以 common_cp.py 为准，不能仅凭模型名称或 PCP 数值判断。
Core 的固定提交已经包含 shard_decode_requests 分支。Ascend 文件中的上游 TODO 注释不能作为“上游完全没有 decode sharding”的证据；这里按实际函数体核对。

三个坐标：global、local、gathered

三个顺序分别回答“请求本来是什么顺序”“本 rank 算哪些行”“collective 后按什么顺序写 KV”。它们不是三个不同的请求池。

坐标长什么样谁使用
global batchScheduler 本步规范的请求 / token 顺序。请求状态、全局 block / slot 映射、恢复后的采样输入。
rank-local batch本 rank 被分配到的 token，可能混合不同请求，含执行 padding。模型前向、局部 query、局部 attention metadata。
padded gathered rowsrank0 的本地行及 padding，接着 rank1，依次拼接。KV collective 后的写入顺序；需要与 gathered slot mapping 一一对应。

用源码自带的字母例子理解映射

global:               [A B C D E F G]
rank0 / rank1:        [A B G] / [C D E F]
padded gathered:      [A B G _ | C D E F]
hidden_restore_idx:   [0,1,4,5,6,7,2]
padded_gather_idx:    [0,1,6,0,2,3,4,5]

gathered[hidden_restore_idx] 恢复 A～G；global[padded_gather_idx] 得到 rank-major 写行。padding 位置的索引即使合法，也必须由 gathered_kv_write_mask 标为不可写，再变成 PAD_SLOT。否则例子中的占位行会误写 A 的缓存。

这是 Core _build_batch_layout 中解释索引含义的教学例子，不是一条长度 7 Prefill 请求按 DualChunkSwap 切分的实测结果。复制 Decode 的重复行也要去重；“参与 gather”不等于“每行都允许落 KV”。

边界固定实现为什么需要

  2. 新 KV 的写行顺序以 gathered slots 和 write mask 为准，不能使用 query 行数来代替。
  3. hidden states 汇集后按 restore indices 回到全局顺序，采样 / draft 有各自边界。
  4. graph / padding / 空 rank 必须服从同一 collective 与写入布局；HiSparse 适配继续复用这些契约。
