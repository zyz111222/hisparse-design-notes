SECTION 01

问题根因：为什么 HiSparse OFF 能走通，ON 却掉回慢路径？

在 vllm-ascend 中，C8 量化稀疏注意力（SFA）在 Prefill 阶段的最优路径是直接调用 CANN 原生 PA_BSND 分页算子（零搬运、硬件页表寻址、无需 argsort）。但同样的模型、同样的权重，HiSparse OFF 时 100% 命中 PA_BSND，HiSparse ON 时却被踢出快路径，根因在于两种模式下的显存分配机制与门禁检查存在本质差异。

HiSparse OFF独立连续池 · 天然无间隙

关闭 HiSparse 时，MLA 主 KV Cache 与 Indexer Cache 按各自独立的内存池连续分配（对应 attn_utils.py:1112-1114 独立分页路径）。MLA 池中相邻两个物理块之间没有任何 HMA 跨组间隙，每块大小严格等于 1 个完整 MLA 页（128 × 656 = 83,968 B），即 block_stride == block_size = 128，page_stride = 1, remainder = 0，原生 PA_BSND 直接用原始 block_table 寻址即可。

HiSparse ON（修复前）HMA 共享池 · 几何错位 + PCP 误杀

开启 HiSparse 后，MLA Resident、Hot 与 Indexer 进入 HMA（Hybrid Memory Allocator）shared-slab 统一共享大池，物理块大小由最大组（22 层 Indexer）决定。由于旧代码仅按单行（656 B）对齐且 Core 重建合成 Spec 时丢弃了对齐约束，导致 attention_block_stride % 128 != 0（remainder != 0）；叠加 PCP > 1 的尾部 padding 长度检查误杀，Prefill 100% 被踢出 PA_BSND。

掉进 stage_prefill_rows 后到底发生了什么？（精准区分 H2D 与 D2D）

很多同学容易误以为“掉进 stage_prefill_rows 就一定会把 KV 从 Host CPU 搬回 NPU”。事实更精细：

  1. 全页常驻时不触发 Host H2D：当上下文全部页都还在 NPU Resident 上（all_context_pages_resident=True）时，stage_prefill_rows 内部的 miss_mask == 0 会跳过 Host→NPU 的 H2D 拷贝（只有真正被驱逐覆盖、miss_mask != 0 的缺失页才会走 Host H2D）。
  2. 但仍有沉重的每层显存与算子开销：即使 miss_mask == 0，每层依然会：① 动态分配一块临时 staged 显存缓冲区；② 执行 2 次 NPU D2D copy（通过 gather_prefill_cache 把分散的 Resident 页搬运并重排进临时 staged 缓冲）+ 空跑一次 hisparse_gather_plan；③ 随后掉进 _C_ascend.npu_kv_quant_sparse_flash_attention_vllm 的 TND 路径，再做物理行映射与 compact_c8_indices（内部含 argsort）。
  3. 叠加 BF16 路径的额外重打包：在非 C8（BF16）模式下，stage_prefill_rows 之后旧代码还会再走 _attention_physical 做一次 sort + pack_attention_rows 逐行重打包，完全没有复用父类 AscendSFAImpl 的分页 PA_BSND 能力。
SECTION 02

HMA 共享池 44 组装箱、640 行（5 页）精确推导与 Hot/Resident 分配

为了彻底理解为什么 A5 上 GLM-5.3（79 层 MLA，其中 78 层主干 + 1 层 MTP L78，配合 22 层 Indexer）在对齐后每个物理块恰好是 640 行（5 个完整 MLA 页 = 419,840 B），我们需要把 HMA 共享池的装箱数学一步步展开。

2.1 从 371,712 B 到 419,840 B（640 行 / 5 页）的精确推导

【已知参数 · A5 GLM-5.3（79 层 MLA + 22 层 Indexer，C8 量化，block_size = 128）】
1. 单行 C8 压缩 KV 宽度：C8_ROW_BYTES = 512 B (int8 NoPE) + 128 B (bf16 RoPE) + 16 B (fp32 scale) = 656 B
2. 单个完整 MLA 页大小：MLA_PAGE_BYTES = 128 行 × 656 B = 83,968 B（约 82 KiB）
3. 4 层打包为 1 个 Resident/Hot 组（如 L0~L3）：4 × 83,968 B = 335,872 B（恰好 4 个 MLA 页）
4. 22 层 Indexer 打包为 1 组（C8 Indexer 单页 = 128 × (128 + 4) = 16,896 B）：
INDEXER_GROUP_BYTES = 22 × 16,896 B = 371,712 B
5. 44 个共享组统一装箱（1 组 Indexer + 20 组 Resident + 21 组 Hot + MTP 尾层等），原始最小物理块大小取各组最大值：
raw_bytes_per_block = max(371,712, 335,872, 83,968, ...) = 371,712 B

【修复前（仅声明单行对齐 656 B）→ 为什么 remainder != 0？】
• 371,712 / 656 = 566.634... → 向上取 656 B 倍数 = 567 × 656 = 371,952 B（或受其他最小对齐约束为 568 行 等）
• 计算页步长：divmod(567, 128) = (4, 55) → remainder != 0！相邻物理块的起始地址相差 4.43 页，PA_BSND 无法用整数 block_table 跳页！

【PR #22716 修复后（整页对齐 83,968 B）→ 精确落到 5 页 = 640 行】
• 在 binding.py 中向共池的 AscendSFAIndexerCacheSpec 及合成 Spec 声明 block_stride_alignment = lcm(..., 83,968)
• Core 向上取整页倍数：ceil(371,712 / 83,968) = ceil(4.4268) = 5 页
• 最终统一物理块大小：aligned_bytes_per_block = 5 × 83,968 B = 419,840 B
• 折合 MLA 行步长：view.attention_block_stride = 419,840 / 656 = 640 行
• 计算页步长：page_stride, remainder = divmod(640, 128) = (5, 0) → 100% 满足 PA_BSND 整页寻址条件！
• 空间代价：单块仅多出 419,840 - 371,712 = 48,128 B（约 +12.9% 块内对齐填充），零拷贝换来 32K TTFT 提速 47.9%。

2.2 48,000 个固定 5 页物理块大池子排布 & PA_BSND 跳页视图

在 HMA 架构下，整个 NPU KV 显存被切分为一块庞大的等长物理块数组（例如 A5 单卡约 48,000 个物理块，每个物理块固定 5 页 = 419,840 B）。任何组（Indexer、Resident、Hot、MTP）向池子申请空间时，拿到的都是这 48,000 个固定大小块中的若干个。通过 view.attention_cache 把同一块底层显存重解释为「连续的 128 行 MLA 页数组」后，原本的逻辑块号 b 只要乘以 page_stride = 5，就能让 PA_BSND 算子精准跳到每个物理块内的有效层页，完美跨过块尾的留空页！

2.3 Hot / Indexer / Resident 三类池的分配与回收关系

Hot 池每请求固定配额

按每请求固定配额 cdiv(device_buffer_size, block_size) 块 × 21 组预留。专门在 Decode 阶段充当 LRU 稀疏热槽，接收由后台 CopyStream 从 CPU Host Source H2D 换入的冷行。

Indexer 池按序列长度常驻

22 层 Indexer 打包为 1 个共享组，随请求上下文长度线性分配物理块并全程常驻 NPU，用于每步快速计算 Top-K 稀疏注意力索引（不参与驱逐）。

Resident 池弹性吃掉剩余块

扣除 Hot 固定配额与 Indexer 占用后，剩余物理块全部归 Resident 弹性使用。Prefill 写入并经 D2H 镜像落盘至 Host Source 后调用 unpin_blocks 释放引用：显存充裕时数据留在 NPU 直读（零搬运），显存紧张时允许新请求按需覆盖回收。

def align_hisparse_indexer_specs(
    specs: dict[str, KVCacheSpec],
    *,
    packed_row_bytes: int | None = None,
) -> dict[str, KVCacheSpec]:
    """向 vLLM Core 的 shared-slab 规划器声明整页对齐约束。

    Core 会在决定总物理块数量之前，把此处的 block_stride_alignment 纳入单块字节数计算；
    Source MLA Spec 及其 CPU Host 布局保持原样不受影响。
    """
    # 1. 参数合法性校验：若外部传入单行字节宽度（C8=656 B，BF16=1152 B），必须为正整数
    if packed_row_bytes is not None and packed_row_bytes <= 0:
        raise ValueError("HiSparse packed row width must be positive")

    aligned = {}
    for name, spec in specs.items():
        # 读取当前 Spec 已声明的步长对齐值（默认通常是 1 或 128）
        alignment = spec.get_block_stride_alignment()
        updates = {}

        if isinstance(spec, AscendSFAIndexerCacheSpec):
            # 校验 Indexer 格式合法性（拒绝当前不支持的 C4 或非法 scale_dim）
            _validate_indexer_spec(spec)
            if spec.cache_sparse_li_c8:
                # C8 Indexer 的 K 与 scale 在页内各自连续存放，需提前把 page_size_padded 预留足
                updates["page_size_padded"] = max(spec.page_size_bytes, spec.page_size_padded or 0)
                alignment = math.lcm(alignment, spec.head_size, torch.float32.itemsize)
            else:
                # 非 C8 Indexer 按自身完整页字节数对齐
                alignment = math.lcm(alignment, spec.page_size_bytes)

            if packed_row_bytes is not None:
                # 【PR #22716 核心修复 A】：
                # Ascend 原生 PA_BSND 要求 shared-slab 的物理块步长对齐到「完整 MLA 页」
                # （block_size * packed_row_bytes，例如 C8 为 128 * 656 = 83,968 B，BF16 为 128 * 1152）。
                # 关键原因：vLLM Core 的 get_hisparse_kv_cache_groups() 在重建合成的
                # HiSparseResidentSpec / HiSparseHotSpec 时会丢弃它们的 block_stride_alignment！
                # 而 AscendSFAIndexerCacheSpec 与它们处于同一个 HMA 共享池中且不会被 Core 丢弃该字段，
                # 因此必须把整页对齐约束挂在共池的 Indexer Spec 上，借它透传给 Core 规划器！
                alignment = math.lcm(alignment, spec.block_size * packed_row_bytes)

        elif packed_row_bytes is not None and isinstance(spec, (HiSparseResidentSpec, HiSparseHotSpec)):
            # 【PR #22716 核心修复 B】：
            # 旧代码写的是 math.lcm(alignment, packed_row_bytes)（仅对齐单行 656 B），
            # 这会导致块步长不是 128 行的整数倍（remainder != 0），从而无法用 block_table * page_stride 寻址。
            # 这里同步升级为整页对齐 spec.block_size * packed_row_bytes，在建池前一次性规划好，
            # 运行时绝不做危险的地址取整。
            alignment = math.lcm(alignment, spec.block_size * packed_row_bytes)

        # 只有对齐值确实变大时才通过 dataclass replace 生成新 Spec，保持原输入对象不可变
        if alignment != spec.get_block_stride_alignment():
            updates["block_stride_alignment"] = alignment
        aligned[name] = replace(spec, **updates) if updates else spec
    return aligned
  • 为什么单行 656 B 对齐不够？单行对齐只能保证每个物理块之间相差整数行（例如 567 行），但 PA_BSND 算子按页（page = 128 行）索引显存，不接受“页内行偏移”。只有对齐到 128 × 656 = 83,968 B，物理块间距才是完整页的整数倍（page_stride = 5, remainder = 0）。
  • 为什么必须挂在共池的 AscendSFAIndexerCacheSpec 上？vLLM Core 的 get_hisparse_kv_cache_groups() 会根据源 MLA Spec 重新构造 HiSparseResidentSpec 与 HiSparseHotSpec，构造过程会丢失之前附加的 block_stride_alignment。而共池的 AscendSFAIndexerCacheSpec 会被 Core 原样保留并参与整个共享池的 lcm 对齐计算，因此挂在它上面是保证整页对齐不丢失的关键“锚点”。
  • 对非 C8（BF16）场景同样生效：只要调用方传入了 packed_row_bytes（如 BF16 的 576 × 2 = 1152 B），if packed_row_bytes is not None: 对 C8 与非 C8 Indexer 一视同仁，均对齐到 128 × 1152 = 147,456 B。

    def _try_c8_resident_prefill(self, query, query_rope, logical_topk, metadata, query_ends, key_lengths):
        # 1. 从 metadata 中拆出 Decode 与 Prefill 的请求数 / token 数
        num_decodes = metadata.num_decodes
        num_decode_tokens = metadata.num_decode_tokens
        num_prefill_tokens = metadata.num_actual_tokens - num_decode_tokens

        # 2. 第一层前置守卫：校验模式、请求结构与张量长度
        if (
            not self.enable_sparse_sfa_c8                             # 仅限 C8 量化模式（BF16 走下方独立分支）
            or metadata.hisparse_for_capture                          # ACLGraph/CUDAGraph 捕获阶段不走此动态路径
            or query_rope is None                                     # SFA 算子需要 RoPE 分量
            or num_prefill_tokens <= 0                                # 本步无有效 Prefill token
            or metadata.num_reqs != num_decodes + metadata.num_prefills  # 必须是标准的 Decode+Prefill 排布
            # 【PR #22716 核心修复 C】：
            # 原代码写死 query.shape[0] == logical_topk.shape[0] == num_prefill_tokens。
            # 在 PCP > 1（如 PCP=2）时，rank 间对齐会在张量尾部补齐 padding 行，
            # 导致 shape[0] > num_prefill_tokens。改为 "<" 放宽门禁，仅拦截长度不足的异常情况！
            or query.shape[0] < num_prefill_tokens
            or query_rope.shape[0] < num_prefill_tokens
            or logical_topk.shape[0] < num_prefill_tokens
        ):
            return None

        # 3. 第二层前置守卫：校验 HiSparse 缓存驻留状态与元数据完整性
        cache = self.hisparse_cache
        view = cache.view
        state_indices = cache.runtime.request_state_indices
        if (
            not cache.all_context_pages_resident                      # 必须全部上下文页均常驻 NPU（无 Host 缺页）
            or cache.dummy_batch                                      # 跳过虚拟填充 batch
            or cache.draft_layer                                      # 跳过 MTP/Draft 投机层
            or view is None                                           # Resident 共享池视图必须已绑定
            or cache.block_table is None                              # 必须有实时 Resident 页表
            or state_indices is None                                  # 必须有请求状态槽索引
            or state_indices.numel() < metadata.num_reqs              # 槽索引数量不能少于当前请求数
            or query_ends.shape != (metadata.num_reqs,)               # 每个请求对应一个累计 query 结束偏移
            or key_lengths.shape != (metadata.num_reqs,)              # 每个请求对应一个历史 KV 总长度
        ):
            return None

        # 4. 第三层前置守卫：严禁在图回放或流捕获状态下执行动态缩放页表
        if (
            get_forward_context().cudagraph_runtime_mode != CUDAGraphMode.NONE
            or torch.npu.is_current_stream_capturing()
        ):
            return None

        # 5. 【PCP 尾部 padding 切片】：
        # 只截取前 num_prefill_tokens 个真实有效 token 送入算子，避免把尾部无效 padding 算进注意力；
        # （外层 _execute_sparse_flash_attention_process L795-L796 会在返回前把尾部自动补 0 恢复原 shape）
        query = query[:num_prefill_tokens]
        query_rope = query_rope[:num_prefill_tokens]
        logical_topk = logical_topk[:num_prefill_tokens]

        # 6. 【几何不变量校验】：确认 HMA 物理块步长恰好是 MLA 页大小（128 行）的整数倍
        # 例如 GLM-5.3：divmod(640, 128) -> page_stride = 5, remainder = 0
        page_stride, remainder = divmod(view.attention_block_stride, view.block_size)
        storage = view.attention_cache
        if (
            remainder != 0                                            # 必须整除，否则无法用整数页表跳页
            or page_stride < 1                                        # 每块至少容纳 1 个 MLA 页
            or not storage.is_contiguous()                            # PA_BSND 要求底层页视图内存连续
            or view.cache.stride(0) != view.attention_block_stride * view.cache.stride(1)
                                                                      # 校验逻辑块跨度与物理行步长严格一致
            or storage.size(0) <= (view.cache.size(0) - 1) * page_stride
                                                                      # 校验页视图总页数足够覆盖最后一个物理块
        ):
            # 6bbc97a1：已移除旧版 Resident TND 兜底，几何不满足时干净返回 None 交由外层处理
            return None

        # 7. 提取 Prefill 请求对应的实时 Resident 页表，并做【非原地】整页缩放
        # state_indices[num_decodes : metadata.num_reqs] 跳过前面的 Decode 请求，只取 Prefill 请求的槽位；
        # clamp_min(0) 防止未分配占位符 -1 乘以 page_stride 变成负数索引；
        # 必须使用非原地 .clamp_min(0).mul(page_stride) 防止污染原始页表引用。
        table = cache.block_table.index_select(0, state_indices[num_decodes : metadata.num_reqs].to(torch.long))
        table = table.clamp_min(0).mul(page_stride)

        # 送入 Prefill 专属算子前，必须切掉前 num_decodes 项，并把每个 Prefill 的结束偏移减去 num_decode_tokens，

        if num_decodes:

            key_lengths = key_lengths[num_decodes:]

        # 经 DeviceOperator.execute_sparse_flash_attention_process 最终调入 CANN 原生
        # torch_npu.npu_kv_quant_sparse_flash_attention(..., layout_kv="PA_BSND", sparse_mode=3, block_table=table)
        # 注意：storage.unsqueeze(2) 补齐 num_kv_heads=1 维度；logical_topk.unsqueeze(1) 补齐头维。
        output = super()._execute_sparse_flash_attention_process(
            query,
            query_rope,
            (storage.unsqueeze(2),),
            logical_topk.unsqueeze(1),
            metadata,
            query_ends,
            key_lengths,
            block_table=table,
        )

        # 10. 进程级一次性日志，方便线上确认确实命中了 PA_BSND 零拷贝快路径及是否混部
        logger.info_once(
            "[hisparse] Resident paged Prefill active (PA_BSND): mixed=%s",
            bool(num_decodes),
            scope="process",
        )
        return output

3.3 改动三：vllm_ascend/attention/sfa_hisparse.py — BF16 Staged Prefill 复用 Paged SFA

当 _try_c8_resident_prefill 返回 None（例如非 C8 BF16 模式，或确实存在缺失页需要从 Host 搬运）时，会进入 stage_prefill_rows 得到紧凑的 staged 缓存与 staged_table。PR #22716 优化了非 C8（BF16）场景，使其直接复用父类 paged SFA，跳过原本耗时的 sort + pack_attention_rows 重打包，并同样支持 PCP padding 切片。

vllm_ascend/attention/sfa_hisparse.py (L748-L797) — 完整源码 + 逐行中文注释（对齐 6bbc97a1）

                    self.index_group_index, host, metadata

                selected = logical[num_decode:]

                if (

                    and self.qk_rope_head_dim                                 # 具有独立 RoPE 维度（需 split latent/rope）
                    and query_rope is not None
                    and not metadata.hisparse_for_capture

                    and query_rope.shape[0] >= num_prefill_tokens
                    and selected.shape[0] >= num_prefill_tokens
                    and actual_seq_lengths_query.shape == (metadata.num_reqs,)
                    and actual_seq_lengths_key.shape == (metadata.num_reqs,)
                ):
                    # 每页只做一次 split(latent, rope)，即使被很多个 query 共同选中也不用重复搬运；
                    # 彻底跳过旧路径 _attention_physical 中的 FP32 sort + pack_attention_rows 重打包！
                    latent, rope = staged.unsqueeze(2).split((self.kv_lora_rank, self.qk_rope_head_dim), dim=-1)
                    prefill_output = super()._execute_sparse_flash_attention_process(
                        query[:num_prefill_tokens],
                        query_rope[:num_prefill_tokens],
                        (latent.contiguous(), rope.contiguous()),
                        selected[:num_prefill_tokens].unsqueeze(1),
                        metadata,

        if result.shape[0] < ql_nope.shape[0]:

算子差异（PA_BSND vs TND）与 A3 / A5 完整四方实测对比

为什么同样都在 NPU 上算稀疏注意力，PA_BSND 能把 TND 甩开一大截，并且促使 PR #22716 在最新提交 6bbc97a1 中果断移除了 Resident TND 兜底？核心差距来自底层算子接口、索引预处理与多请求混部下的执行开销。

SECTION 05

延伸理解：HostMirrorConnector 步内 draft defer 与 Prefill D2H 尾巴

打通 PA_BSND 后，A5 32K/128 C=1 的 TTFT 从 11.890 s 骤降到 6.193 s，但与 HiSparse OFF（4.996 s）相比仍有约 +1.20 s（+23.97%）的固定差距。这部分已不再来自注意力算子本身，而是来自 HostMirrorConnector 在 Prefill 步末同步等待 D2H 镜像尾巴：

  • 层间全程异步掩盖：第 1~78 层每层写完 Resident 后立即调用 submit_layer_mirror，由独立 DMA/CopyStream 在后台把 KV 镜像写向 CPU Host Source，与后续层 NPU 计算并行重叠。
  • 步末同步防止跨步写花：由于 Scheduler 在相邻两步（chunk）之间可能释放、驱逐或重分配物理块，所有在途 D2H 必须在 finalize_step() 之前完成同步落盘，不能放任跨步悬空异步。
  • 步内 draft defer 仅对纯 Decode 生效：host_mirror.py:169 显式限定仅在 not input_batch.has_prefill 且无 padding 时，才把 D2H 同步推迟到 MTP/Draft 投机层计算之后（从而把 Decode 的少量 D2H 完全藏进 Draft 计算时间里）。而在 A5 TP4 × PCP2 这种高算力、单卡 Prefill D2H 流量大的场景下，78 层计算跑完时 DMA 队列往往还剩约 1.2~1.3 s 的镜像尾巴，只能在 finish_forward() 处当场等完——这属于 HiSparse 异步镜像的架构边界，后续需通过独立的跨步/流水优化专题推进，不在本 Bugfix PR 范围内。
