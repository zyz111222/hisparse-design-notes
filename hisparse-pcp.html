PCP 的核心设计：Query 行与 KV 写入行分开

PCP 并不自动要求新写一套 HiSparse 缓存管理器。本补丁让 Core 继续看规范的请求布局，同时把 query 和 gathered write 的地址分别接对。

字段 / Buffer代表什么消费者
hisparse_request_state_indices本 rank query 对应的持久 request state。每层 Runtime 的 Resident / Hot 解析。
hisparse_num_write_tokensall_gather 后需要考虑的写入行数；不等于本地 query 行数。write_target、Host mirror 的切片与容量。
hisparse_num_valid_write_rows有效写入行的设备标量，用于固定图几何下的有效范围。PCP scatter；padding 仍需 write mask / 无效 slot。
hisparse_write_has_prefill全局写入中是否有 Prefill，来源 pcp_has_global_prefill。镜像策略；不能只看本 rank 是不是 Decode batch。
write_req_id_per_token每个 gathered write row 属于哪个规范请求；无效行标 -1。新 Host 写入对应的 Hot invalidation。
_gathered_kv_slot_mappingsall_gather 行顺序对应的 Resident / Host 写入位置。新 KV scatter 与 D2H 镜像。
_local_block_tables服务本地 query 的 Source / Hot 查表视角。Runtime query 读路径；不拿它替代全局镜像目标。
教学例子（只解释布局，不代表固定切分算法）：假设某步 PCP=2，每 rank 本地有 2 行。rank0 算 [a,b]，rank1 算 [c,pad]，gather 后物理行序是 [a,b,c,pad]。rank0 的 query 仍只有 [a,b]；Resident 与 Host 镜像必须覆盖全局有效写行 [a,b,c]，pad 被 mask。若按本地 query 行数截断镜像，就会漏掉 c；若把 pad 认作真实请求，就会污染缓存。

PCP 的执行时序：本地生产，字节聚合，全局写入，本地查询

PCP 的 KV all_gather 与 HiSparse 的 Host → Hot 是两次不同的数据移动。它们分别解决新 KV 的一致写入和历史稀疏读取。

  1. 为什么先写 scratch？prolog 接收的是本地 token 的输入。直接把 all_gather 后的 global slots 传给本地写操作，会把输入行与目标行错配。先生产本地 packed rows，聚合后再 scatter。
  2. 为什么按字节聚合？C8 行内有 FP8、BF16 与 FP32 三种组成；对整个容器错误地按一种浮点数解释或重排，会破坏 RoPE 和 scales。
  3. 为什么还要全局 batch？Core Coordinator 生成的 request row_mirrors 和 Source block table 基于规范请求。wrapper 通过全局请求恢复 gathered row 的归属，让 D2H 与 invalidation 覆盖正确请求。
  4. 为什么本地 state 不能复用全局顺序？query 已按 rank 改变位置；LRU / Resident 的状态索引仍是持久请求索引，传错会跨请求命中。

图模式与 MTP：固定几何不等于固定请求内容

同一套 buffer 在捕获和回放之间地址要稳定，内容则每步更新。Target 与 Draft 的 query / write 布局还会在一个 step 内发生变化。

路径Query / KV 写入特征本补丁接法
Target Prefill / request-sharded Target Decode本地 queries；需要聚合时使用 rank-major KV writes。local query tables + gathered Resident / Host slots。
Draft Prefill复用 target 的 PCP query / gathered KV 布局。prepare_draft_prefill() 绑定相同方向的 slots / tables。
后续 replicated Draft Decode每 rank 做复制的草稿步骤，不做同样的 KV gather。prepare_draft_decode() 回切 global tables / slots，并复制对应 draft state。
capture / replaygraph warmup 可绕过正常 connector.pre_forward。构造 wrapper 时提前绑定持久 slots / tables；query states 和 valid rows 使用持久 buffer。
FULL graph 镜像逐层 Python finish_kv_update 不随每次 replay 执行。避免 capture 时错误提交镜像；forward 完成后走 worker 镜像与事件。
为什么改到 vLLM 类的方法？Core 原接口把部分 query 行数 / has_prefill 与写入视角绑定在一起；PCP gather 后二者不再相等。当前选择在 Ascend 内安装有限的运行时适配，Core 文件没有改动，但 Core 对象的部分运行行为确实被扩展。
被适配的方法改动目的
HiSparseCacheHandle._prepare_for_batch先调用 Core 原方法，再绑定 PCP 的 query state、write count、write IDs 和镜像条件。
HiSparseCacheHandle.write_targetgathered write 不能按本地 Decode query 数误截断。
HiSparseCacheHandle.finish_kv_update根据全局 write_has_prefill 和 graph 模式安排镜像。
HiSparseConnectorWorker._clear_forward_mirror_state保留 Core 清理逻辑，再清理新增的 write 视角字段。
HiSparseConnectorWorker._enqueue_host_mirror使用 gathered write 的行数、slots 与 request IDs；调用 Core 行 DMA。

混部与 PD 分离：计算相似，缓存交付边界不同

Prefill 的模型计算可以相同，但 PD 中的 P 与 D 是两个引擎。P 的本地 Resident 状态、设备块编号和完成事件，不能直接成为 D 的本地状态。

维度混部PD 分离
请求与页状态同一引擎连续维护。P / D 各自维护；通过传输协议交付可复用 KV。
Host Source 的身份本地卸载池。D 端必须有自己的目标页；不能只拿到 P 的本地页号。
Indexer KV本地计算 / 保留。稀疏模型后续 Decode 还需要对应 Indexer 历史，不只是主 KV。
Resident / Hot在本地分配与淘汰。layout 标记为不参与交付；D 自己建立这些临时副本。
“完成”的含义本地写回完成足以支撑本地 Host 后备。还要证明远端 load 完成、D 的对应组已填好，之后才能建立有效历史。
PCP 的位置一个引擎内部 query / KV 的并行布局。P、D 各自可有不同并行配置，外部 connector 还要解决布局与组兼容；当前补丁没有接通。

组合矩阵：把“设计接口”和“当前支持”分开

P 端不开 HiSparse 是合理的部署目标，但它不是只在开关上少写一个参数：P 的输出布局仍要能交付给 D 的 Host Source 和 Indexer。

部署 / 组合本地 KV 路径固定版本的结论
混部，PCP=1，HiSparse 开Resident 写入；Host 后备；Decode Hot 换入。Ascend 基础路径；CPU / NPU 验证记录需要按具体提交看，不能由设计图直接证明收益。
混部，PCP>1，HiSparse 开本地 query 与 gathered KV writes 分开；Host 镜像全局写行。本文 PCP 分支已实现 C8 + request-sharded target decode；非基础 PR 自带支持。
PD：P / D 都不开 HiSparse常规 PD 传输。不属于本文 HiSparse 适配证明范围；不能据此推导下一行自动可用。
PD：P 不开、D 开 HiSparse需要把 P 主 KV 映射到 D Host Source，并交付 Indexer；D 建本地临时缓存。Core 的 region / mixed memory 机制可用于分析；当前 Ascend PCP wrapper 未支持外部 connector 组合，不写成可运行方案。
PD：P / D 都开 HiSparse可交付组是 Source / Indexer；Hot / Resident 留在各自本地。Core 有 MultiConnector 与 Host import 接口；当前 Ascend PCP 分支未打通 / 未验。
PD + PCP + HiSparse同引擎 PCP 行布局与跨引擎传输布局同时需要正确。当前未支持；不能绕开 direct connector 检查就认定完成。
DCP + HiSparseDecode context 另有切分语义。当前 AscendHiSparseImpl 明确拒绝 DCP。
当前 PCP 分支约束代码位置 / 解释
C8 原生几何E4M3FN，NoPE512 / RoPE64，FP32 scales，tile 128；PCP 要求 request-sharded target decode。
直接 HiSparse connectoradapter 要求 runner wrapper 是 ActiveKVConnector，内部精确为 HiSparseConnector。
私有 Host 的重叠路径HostMirrorConnector 的安装条件排除 shared_host_region；不把 CPU rank0 共享写机制当作当前 NPU 路径。

把整体收回来：本地分层缓存是主体，PCP 和 PD 改不同边界

这套设计复杂的地方，在数据生命周期与地址空间的一致性，而不只是多写几个 kernel。

一层层看最终记住的设计责任
HiSparse 本体Host 提供历史后备；Resident 保留可直接读的页；Hot 缓存缺失页中的稀疏 token。
Core 控制面页分配、写回完成、驻留回收、前缀发布与释放，统一走 Coordinator / Managers / Connector。
Core / Ascend 数据面TopK 解析 → 只搬 miss → 等本层 ready → Sparse Attention；NPU backend 承接平台操作。
PCP 适配保留规范请求的控制面；把本地 query state 与全局 gathered KV / mirror writes 拆开；图与 MTP 也沿这个区分。
PD 适配在本地机制外增加跨引擎组映射与交付完成；D 重新建立本地 HiSparse 状态。当前 Ascend PCP 分支还未覆盖。
